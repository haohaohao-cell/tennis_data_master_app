# 网球数据库设计

本设计对应当前核心业务模型：

```text
User 1 ─── N TennisActivity
Lesson 1 ─── N TennisActivity
Lesson 1 ─── N LessonStudent
TennisActivity 1 ─── N Video
Video 1 ─── N Point
Point 1 ─── N Shot
Video 1 ─── N VideoShare
SocialPost N ─── 0..1 TennisActivity
SocialPost 1 ─── N PostMedia
PostMedia N ─── 0..1 Video
```

核心边界：

- `videos` 是原始视频资产，保存文件、上传者、所有者、分析状态和可见性。
- `tennis_activities` 是某个用户自己的网球活动记录，必须且只能属于一个用户。
- `lessons` 是教练课程容器，用于组织教练、学生、教学记录和课程内活动。
- `social_posts` 是用户主动发布的社交动态，不等于原始视频或完整活动。
- 旧 `uploads` 不再作为核心业务表使用；视频分析结果通过 `points.video_id` 关联到 `videos.video_id`。

所有表统一包含：

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `created_at` | TIMESTAMPTZ | 创建时间 |
| `updated_at` | TIMESTAMPTZ | 更新时间 |
| `deleted_at` | TIMESTAMPTZ NULL | 软删除时间 |

SQLite 实现中 UUID 和 TIMESTAMPTZ 使用 `TEXT` 保存，布尔值使用 `0/1`。

## 一、users 用户表

一条记录代表一个 App 用户。用户可以是普通球员，也可以具备教练身份。

| 字段 | 类型 | 是否为空 | 默认值 | 含义 |
| --- | --- | --- | --- | --- |
| `user_id` | UUID | 否 | 自动生成 | 用户主键 |
| `nickname` | VARCHAR(50) | 否 |  | 昵称 |
| `avatar_path` | TEXT | 是 |  | 头像路径 |
| `phone` | VARCHAR(30) | 是 |  | 手机号 |
| `email` | VARCHAR(255) | 是 |  | 邮箱 |
| `status` | VARCHAR(20) | 否 | `active` | 用户状态 |
| `playing_hand` | VARCHAR(10) | 否 | `right` | 持拍手 |
| `is_coach` | BOOLEAN | 否 | `false` | 是否具备教练身份 |
| `coach_status` | VARCHAR(20) | 是 |  | 教练身份状态 |
| `coach_verified_at` | TIMESTAMPTZ | 是 |  | 教练认证时间 |

枚举：

```text
status: active, disabled, deleted
playing_hand: right, left, unknown
coach_status: pending, active, disabled, rejected
```

约束与索引：

- `PRIMARY KEY (user_id)`
- `UNIQUE INDEX lower(email) WHERE email IS NOT NULL AND deleted_at IS NULL`
- `UNIQUE INDEX phone WHERE phone IS NOT NULL AND deleted_at IS NULL`
- `INDEX (is_coach, coach_status)`
- `is_coach = false` 时 `coach_status IS NULL`
- `coach_verified_at` 非空时，要求 `is_coach = true AND coach_status = active`

说明：

- 教练身份不是独立账号；`is_coach`、`coach_status`、`coach_verified_at` 是兼容字段。
- 完整教练身份、类型、暂停和撤销状态以 `coach_profiles` 为准；申请和审核历史以 `coach_applications` 为准。

## 二、coach_applications 教练身份申请表

一条记录代表用户提交的一次教练身份申请。用户被拒绝后重新申请时创建新记录，保留历史审核原因。

| 字段 | 类型 | 是否为空 | 默认值 | 含义 |
| --- | --- | --- | --- | --- |
| `coach_application_id` | UUID | 否 | 自动生成 | 教练申请主键 |
| `applicant_user_id` | UUID | 否 |  | 申请用户 |
| `application_type` | VARCHAR(30) | 否 |  | 申请类型 |
| `status` | VARCHAR(20) | 否 | `pending` | 审核状态 |
| `display_name` | VARCHAR(50) | 否 |  | 教练展示名称 |
| `real_name` | VARCHAR(50) | 是 |  | 真实姓名 |
| `phone` | VARCHAR(30) | 是 |  | 联系电话 |
| `city` | VARCHAR(80) | 是 |  | 所在城市 |
| `specialties` | VARCHAR(255) | 是 |  | 擅长方向 |
| `coaching_experience` | TEXT | 是 |  | 教学或训练经历 |
| `certification_title` | VARCHAR(120) | 是 |  | 资质名称 |
| `certification_file_path` | TEXT | 是 |  | 资质证明文件路径或 URL |
| `verification_video_path` | TEXT | 是 |  | 打球、教学或技术展示视频路径或 URL |
| `note` | TEXT | 是 |  | 申请补充说明 |
| `reviewer_user_id` | UUID | 是 |  | 审核管理员 |
| `reviewed_at` | TIMESTAMPTZ | 是 |  | 审核时间 |
| `rejection_reason` | VARCHAR(500) | 是 |  | 拒绝原因 |
| `created_at` | TIMESTAMPTZ | 否 | 当前时间 | 创建时间 |
| `updated_at` | TIMESTAMPTZ | 否 | 当前时间 | 更新时间 |

枚举：

```text
application_type: certified, non_professional
status: pending, approved, rejected, canceled
```

约束与索引：

- `applicant_user_id REFERENCES users(user_id)`
- `reviewer_user_id REFERENCES users(user_id)`
- `application_type = certified` 时 `certification_file_path` 必填
- `application_type = non_professional` 时 `verification_video_path` 必填
- `UNIQUE INDEX (applicant_user_id) WHERE status = pending`
- `INDEX (status, created_at DESC)`

## 六、tennis_activities 网球活动表

一条记录代表某个用户自己的网球活动记录。课程内的教练示范和学生训练也分别是各自用户的活动记录。

| 字段 | 类型 | 是否为空 | 默认值 | 含义 |
| --- | --- | --- | --- | --- |
| `tennis_activity_id` | UUID | 否 | 自动生成 | 活动主键 |
| `owner_user_id` | UUID | 否 |  | 活动所有者 |
| `lesson_id` | UUID | 是 |  | 所属课程；普通活动为空 |
| `title` | VARCHAR(120) | 是 |  | 活动标题 |
| `activity_type` | VARCHAR(30) | 否 | `other` | 活动类型 |
| `default_visibility` | VARCHAR(30) | 否 | `private` | 默认可见性 |
| `started_at` | TIMESTAMPTZ | 是 |  | 开始时间 |
| `ended_at` | TIMESTAMPTZ | 是 |  | 结束时间 |
| `location_name` | VARCHAR(120) | 是 |  | 场地名称 |
| `court_surface` | VARCHAR(30) | 是 |  | 场地类型 |
| `opponent_user_id` | UUID | 是 |  | 对手用户 |
| `opponent_name` | VARCHAR(50) | 是 |  | 非注册对手显示名 |
| `note` | TEXT | 是 |  | 用户备注 |
| `analysis_summary_status` | VARCHAR(30) | 是 |  | 活动级分析汇总状态 |

枚举：

```text
activity_type:
casual_hit, match, serve_training, forehand_training, backhand_training,
multi_ball_drill, stroke_recording, post_match_review, lesson_practice,
coach_demo, other

default_visibility:
private, friends, specified_users, lesson_coach, lesson_participants, public

analysis_summary_status:
pending, processing, completed, failed

location_source:
device_gps, video_metadata, manual_legacy, unavailable

location_coordinate_system:
wgs84, gcj02
```

定位口径：

- App 采集并保存的 Activity 经纬度使用 `wgs84`。
- App 前台运行时维护内存级位置缓存：启动和回到前台时刷新一次，前台每 3 分钟刷新一次；业务创建/发布流程优先使用最近一次缓存坐标。
- App 不调用手机系统反地理编码；拿到经纬度后调用后端行政区解析接口补全省、市、区。
- `video_metadata` 表示上传或发布所选视频文件/相册资产自带的拍摄经纬度，优先于当前手机定位缓存。
- 后端行政区解析使用 AreaCity 三级行政区边界数据、Shapely 和 STRtree，不在本阶段引入 PostGIS；默认读取 `backend/data/area_city_ok_geo.csv`，同时支持 GeoJSON/JSON 边界文件；API 启动时预热边界索引，正常解析请求不承担大文件冷加载成本。
- 边界数据坐标系由 `TENNIS_AREA_CITY_COORDINATE_SYSTEM` 配置，默认 `gcj02`；查询前后端负责把手机 `wgs84` 坐标转换到边界坐标系。
- 经纬度获取成功且边界数据可用时，后端返回精确命中或最近行政区近似结果；只有解析依赖、边界数据不可用或客户端请求超时时，仍保存经纬度，`location_city` / `location_district` 可为空。

约束与索引：

- `PRIMARY KEY (tennis_activity_id)`
- `owner_user_id REFERENCES users(user_id)`
- `lesson_id REFERENCES lessons(lesson_id)`
- `opponent_user_id REFERENCES users(user_id)`
- `INDEX (owner_user_id, created_at DESC)`
- `INDEX (lesson_id, created_at DESC)`
- `INDEX (activity_type, started_at DESC)`
- `INDEX (location_city, location_district, started_at DESC, tennis_activity_id DESC) WHERE deleted_at IS NULL`
- 应用层校验：课程内活动的 `owner_user_id` 必须是该课程教练或该课程学生。

## 八、video_shares 视频分享表

| 字段 | 类型 | 是否为空 | 默认值 | 含义 |


## 十一、Feed 行为与统计表

内容流不把互动统计、用户浏览和用户隐藏临时拼接到 `social_posts`。这些数据独立落库，便于后续推荐、统计和行为分析扩展。

### `social_post_stats` Post 统计表

每条 Post 一条统计记录，保存点赞、评论、收藏、分享和浏览总数。`social_post_id` 为主键并引用 `social_posts`。

| 字段 | 含义 |
| --- | --- |
| `social_post_id` | Post 主键 |
| `like_count`、`comment_count`、`favorite_count`、`share_count` | 基础互动计数 |
| `view_count` | 浏览总数 |
| `updated_at` | 统计更新时间 |

### `user_post_views` 用户 Post 浏览记录

一条记录表示一个用户是否看过一条 Post。当前首页只要求识别已看内容并在排序中后置，但表结构预留浏览来源、首次/最近浏览时间、停留时长和浏览次数。

| 字段 | 含义 |
| --- | --- |
| `user_post_view_id` | 浏览记录主键 |
| `user_id`、`social_post_id` | 浏览用户和被浏览 Post |
| `first_viewed_at`、`last_viewed_at` | 首次和最近浏览时间 |
| `first_view_source`、`last_view_source` | 浏览来源，例如 `home_feed` |
| `view_count` | 浏览次数 |
| `total_dwell_time_ms`、`last_dwell_time_ms` | 累计和最近一次停留时长 |

约束：`UNIQUE (user_id, social_post_id)`，批量重复上报使用 upsert，不生成重复记录。

### `user_post_hides` 用户主动隐藏记录

保存用户主动隐藏某条 Post 的状态。`status = active` 时首页推荐、关注和附近流统一排除；取消隐藏只更新为 `canceled`，不删除历史。

| 字段 | 含义 |
| --- | --- |
| `user_post_hide_id` | 隐藏记录主键 |
| `user_id`、`social_post_id` | 用户和 Post |
| `status` | `active` 或 `canceled` |
| `source`、`reason` | 隐藏来源和原因 |
| `hidden_at`、`canceled_at` | 隐藏和取消时间 |

约束与索引：

- active `(user_id, social_post_id)` 唯一
- `user_post_views(user_id, last_viewed_at DESC, social_post_id DESC)`
- `user_post_hides(user_id, hidden_at DESC)`
- 所有用户和 Post 字段均使用外键引用现有主表

### Post 互动、消息请求、隐私与举报补充表

第一版社交互动不把点赞、收藏、评论和分享只存成计数字段。`post_reactions` 保存点赞事实，`post_favorites` 保存收藏事实，`post_comments` 统一保存评论和回复，`post_shares` 保存分享行为；`social_post_stats` 仍作为展示和排序缓存。active 点赞 `(user_id, social_post_id, reaction_type)` 唯一，active 收藏 `(user_id, social_post_id)` 唯一。

陌生人消息请求由 `chat_message_requests` 保存，`pending` 状态下 `(requester_user_id, recipient_user_id)` 唯一。接受请求后创建或复用双方 direct conversation，并把 `conversation_id` 写回请求记录。

基础隐私控制由 `user_privacy_settings` 保存，第一版包含私信策略、是否接受消息请求、默认 Post 可见性和陌生人资料可见开关。举报由 `content_reports` 保存，同一用户对同一对象只能有一条 `pending` 或 `reviewing` 举报。

## 十三、shots 每拍表

一条记录代表一次球拍触球事件，以及本次触球后产生的球轨迹摘要。

字段、枚举、单位、跨字段关系以 `docs/data/tennis_global_data_dictionary.md` 中 `shots` 字典为准。

核心约束：

- `point_id REFERENCES points(point_id) ON DELETE CASCADE`
- `UNIQUE (point_id, shot_index)`
- 发球拍要求 `shot_role = serve`、`serve_number IN (1, 2)`、`stroke_type = serve`
- 非发球拍要求 `serve_number IS NULL`
- `is_point_ending = true` 时 `point_winner_slot` 必须为 `A` 或 `B`

## 十四、可见性规则

视频访问建议按以下顺序判断：

```text
1. 当前用户是否是 videos.owner_user_id
2. 当前用户是否是 videos.uploader_user_id
3. 是否存在 active 且未过期的 video_shares
4. 检查 videos.visibility
5. videos.visibility = inherit 时读取 tennis_activities.default_visibility
6. 活动属于 lesson 时，根据 lessons.coach_user_id 和 lesson_students 判断课程关系
7. public 内容允许公开访问
8. 其他情况拒绝
```

课程默认规则：

- 学生自己的课程活动：学生本人和本节课教练可见，其他学生默认不可见。
- 教练自己的课程活动：教练本人可见，可显式分享给某个学生或整节课学生。
- 同课学生之间默认不互相可见，除非设置为全课可见或通过 `video_shares` 显式分享。

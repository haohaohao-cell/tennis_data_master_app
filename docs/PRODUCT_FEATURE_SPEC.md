# 网球活动、视频、课程与动态的业务逻辑说明

本产品的核心是帮助用户记录、分析、管理和分享自己的网球活动。

大部分使用场景是普通球友日常打球，例如对拉、比赛、发球练习、动作录像、朋友约球、赛后复盘等。课程是其中一个重要场景，主要服务于教练和学员，用于教学记录、视频共享、动作分析、课后反馈和学员档案管理。

系统需要同时支持普通用户的日常打球记录，也要支持教练和学员之间更结构化的课程管理。

## 0. 产品命名

本项目对内称为“网球数据系统”，强调它是覆盖 App、后台、数据、视频分析和课程管理的完整系统。

移动端 App 暂定名称为“网球日记”，对外文案和 App 端用户界面应优先使用这个名称，避免把内部系统名直接暴露给普通用户。

## 当前代码同步摘要（2026-08-02）

当前代码已经形成 App、backend、Admin Web、CV 与 shared schema 分层协作的第一版产品骨架。backend 已接入 `/api/v1/auth`、`/api/v1/users`、上传与 Activity、Post 与 Feed、我的内容聚合、社交关系、消息与通知、隐私、举报、Admin 管理等 API；Admin Web 通过管理员接口管理用户、教练申请、Activity、视频和 Post；移动端已接入真实登录、资料与头像、首页 Post Feed、Post 发布与详情、Activity 上传与详情、我的内容页、基础消息中心、用户搜索、关注、私信和教练身份申请。

当前仍属于演示或占位的移动端范围包括：训练页的本周概览和最近活动列表、训练页“课程”记录入口、教练工作台的学员/课程/待点评视频数据、学员档案页、球员“数据”Tab、AI 分析指标与训练建议、完整课程管理、视频批注、Activity 剪辑发布入口、拉黑/隐私设置/举报/Post 分享/群聊创建等用户端入口。CV 侧已有推理管线与数据持久化模块，但 App 和 backend 当前主要使用 `analysis_status` 展示排队、处理中、完成或失败状态，尚未把真实 AI 分析结果填充到移动端图表和建议模块。

## 1. 视频是原始素材

用户可以上传或录制视频。

视频只是一个原始素材，例如：

* 一段比赛录像
* 一段正手动作特写
* 一段发球练习视频
* 一段教练示范视频
* 一段课堂训练视频
* 同一次活动中的不同机位视频

视频本身不等于一次完整的网球活动，也不等于一节课程，也不等于一条社交动态。

用户可以把一个或多个视频整理到某次网球活动中，也可以从视频中选择片段发布动态。

## 2. 网球活动是用户自己的打球记录

网球活动表示某个用户自己的一次打球记录。

常见类型包括：

* 球友对打
* 业余比赛
* 发球训练
* 正反手练习
* 多球训练
* 动作录像
* 赛后复盘
* 教练课中的个人练习记录

每条网球活动都属于一个用户。

即使两个人一起打球，每个人也可以有自己的活动记录、视频、备注和分析结果。

例如，张三和李四一起打一场球：

* 张三可以创建自己的网球活动，保存自己拍的视频和数据。
* 李四也可以创建自己的网球活动，保存自己拍的视频和数据。
* 两人可以互相分享视频，但不应该强行合并成同一条个人记录。

## 3. 一次网球活动可以包含多个视频

一次网球活动可以关联多个视频。

例如：

* 同一场比赛的全场视频和动作特写
* 手机拍摄视频和高位机位视频
* 一次训练中的发球视频、正手视频、反手视频
* 一次对打中的完整录像和精彩片段
* 一节课中某个学生自己的动作视频和练习视频

用户后续可以基于这些视频查看 AI 分析结果、做视频批注、生成集锦或发布动态。视频分析会将疑似触网作为事件输出，供回合和击球结果判断使用；该事件是算法候选，不替代人工裁判结论。

## 4. 课程是重要的教学场景

课程用于支持教练和学员之间的教学管理。

一节课程通常包含：

* 一个教练
* 一个或多个学生
* 上课时间和场地
* 本节课训练内容
* 教练示范视频
* 学生训练视频
* 教练评价
* 视频批注
* 课后作业
* 下节课重点
* 学员历史记录

课程不是某一个人的视频合集，也不是某一个人的网球活动记录。
课程更像是一个教学场景，用来组织教练、学生、训练内容、评价、作业和相关活动记录。

## 5. 同一节课中，每个人可以有自己的网球活动

在同一节课中，教练和学生都可以产生自己的网球活动记录。

例如：

* 教练可以录制教学示范、技术讲解、课堂回顾。
* 学生 A 可以录制自己的正手训练视频。
* 学生 B 可以录制自己的发球训练视频。
* 学生 C 可能参加了课程，但没有录制视频。
* 教练可以针对不同学生写不同评价和课后任务。

所以，同一节课不应该只有一条混合所有人的网球活动记录。

更合理的理解是：

```text id="5neobc"
一节课程
├── 教练自己的教学记录
├── 学生 A 自己的训练记录
├── 学生 B 自己的训练记录
├── 学生 C 的课程参与记录
└── 教练对每个学生的评价和作业
```

这样既能支持课程管理，也不会破坏“网球活动属于个人”的核心逻辑。

## 6. 学生不一定会录视频

课程中需要特别注意：学生参加了课程，不代表他一定录制了视频。

例如：

* 学生只是跟着上课，没有录视频。
* 学生的视频由教练统一录制。
* 学生只参与训练，没有上传任何素材。
* 教练仍然需要记录这个学生的表现、评价、作业和下节课重点。

所以课程需要有明确的学生名单和教学记录，不能只根据“谁上传了视频”来判断谁参加了课程。

## 7. 课程中的视频共享

课程场景下，视频共享应该符合教学关系。

常见情况包括：

* 学生录制自己的训练视频，并共享给教练。
* 教练查看学生视频后，做评价、批注或反馈。
* 教练录制示范视频，并共享给一个学生或整节课的学生。
* 教练针对某个学生录制纠正视频，只分享给该学生。
* 同一节课的学生之间默认不互相可见，除非用户明确设置为全课可见或主动分享。

因此，课程视频的归属和可见性需要保持清楚：

* 学生录的视频，仍然属于学生。
* 教练录的视频，仍然属于教练。
* 课程负责组织这些内容的教学关系。
* 用户仍然可以控制每个视频的可见范围。

## 8. 课程中的视频批注和教学反馈

课程功能不只是保存视频，还应该支持教学反馈。

教练可以围绕视频做：

* 时间点批注
* 动作问题标记
* 语音或文字点评
* 慢放、循环播放、暂停讲解
* 技术动作对比
* 本节课总结
* 课后训练建议

这些批注和反馈应该服务于教学，不应该直接改变原始视频本身。
视频仍然是原始素材，批注是附加在视频和课程上的教学信息。

## 9. 教练端需要支持学员档案

课程功能还应该服务于教练管理学员。

教练需要查看某个学生的长期记录，例如：

* 上过哪些课
* 每节课训练了什么
* 每次课的视频
* 每次课的表现评价
* 常见技术问题
* 历史作业完成情况
* 技术进步趋势
* AI 分析数据变化

这样，课程就不仅是一条上课记录，也会逐渐形成学员的训练档案。

## 10. 可见性以用户控制为核心

用户上传的视频和活动默认应该由用户自己控制可见范围。

普通打球场景中，用户可以选择：

* 仅自己可见
* 分享给好友
* 分享给指定用户
* 发布到社交动态
* 公开可见

课程场景中，可以有一些默认共享规则：

* 学生的视频默认可以让教练查看，方便教学反馈。
* 教练的视频可以分享给某个学生，也可以分享给整节课的学生。
* 同一节课的学生之间默认不互相可见。
* 如果用户明确设置为全课可见或主动分享，其他学生才可以查看。

## 11. 社交动态是主动发布的内容

社交动态是用户主动发布到社区里的内容。

动态可以来自某次网球活动，也可以引用其中的一段视频、一个精彩回合、一张数据卡片或一段训练成果。

例如：

* 发布一个精彩回合
* 发布一段发球动作
* 发布“今天正手连续对拉 42 拍”
* 发布一场比赛的集锦
* 发布教练教学视频

动态不等于原始视频，也不等于完整活动记录。
用户发布动态时，只是在选择性分享某些内容，不应该自动改变原始视频或原始活动记录的隐私设置。

## 12. 核心业务边界

本产品需要始终保持以下边界清晰：

* 视频是原始素材。
* 网球活动是用户自己的打球记录。
* 课程是教练和学生之间的教学场景。
* 动态是用户主动发布的社交内容。

普通用户的主要场景是日常打球记录、视频分析和社交分享。
教练和学员的主要场景是课程管理、视频反馈、学员档案和持续训练跟踪。

课程功能很重要，但它应该作为网球活动体系中的教学扩展，而不是替代普通用户的打球记录逻辑。

## 13. 注册登录与用户身份

移动端需要通过后端认证接口完成登录，不使用纯前端假登录。当前开发期只开放手机号验证码登录，验证码固定为 `000000`；手机号首次登录时后端自动创建用户，再次登录同一手机号应进入同一个用户账户。

系统内部所有业务数据必须以 `user_id` 关联用户。手机号、微信 openid、Apple subject 等只属于登录身份，不作为业务主键。当前已预留用户表、登录身份表和会话/token 表结构，后续接入真实短信、微信登录、Apple 登录、账号绑定或账号注销时，不应推翻现有用户体系。

App 启动时应尝试恢复本地登录状态，但不应在进入 App 时强制弹出登录页。未登录用户可以浏览首页视频流、训练页概览、消息占位内容和公开/模拟内容；当用户进入“我的”页时展示登录/注册入口。点赞、评论、收藏、发布、上传视频、创建活动、查看或管理个人归属数据等需要用户身份的操作，应在触发时提示登录。已登录用户的“我的”页不展示手机号；资料状态标签展示“资料待完善”或“资料已完善”，点击后进入账号资料页完善昵称和主要持拍手。我的页面右上角菜单提供账号资料、教练身份和设置入口；退出登录位于设置页底部，需二次确认，完成后清理本地登录状态并注销当前服务端会话。

会话持久化使用 access token 与 refresh token。原生移动端优先使用平台安全存储；Web 端使用 localStorage；安全存储不可用时，原生端只使用内存会话作为开发兜底，不应被视为跨重载的稳定登录状态。启动恢复会话时，临时 API 或网络失败不应立即删除本地会话；只有 refresh token 已过期，或后端明确返回认证失败时，才清理本地登录状态。

登录页右上角提供关闭按钮。用户从需要登录的操作进入时，点击后应优先返回来源页；当没有可返回的历史页面时，回到主 Tab。微信登录入口可以展示在登录页，但当前不可用，点击时提示“微信登录将在正式版开放，请先使用手机号登录”。

账号资料页支持用户从相册选择头像并在保存资料时上传。头像文件由后端保存为受控公开路径，写入 `users.avatar_path`，移动端“我的”页、动态作者、评论作者等头像展示统一读取该字段并通过媒体 URL 解析展示；未设置头像时继续使用昵称首字母占位。

## 14. 移动端第一版 UI 框架

第一版移动端用于确认整体页面结构、真实数据接入方式和视觉方向。当前已接入开发期后端登录、用户身份、头像上传、真实视频上传、Activity 创建、Post 发布、首页 Feed、Post 详情、Post 站内分享、评论分页/回复/删除、我的内容聚合、基础消息中心、用户主页、球友搜索、私信和教练身份申请；训练页部分概览、教练工作台、学员档案和 AI 数据仍保留演示或占位内容。视觉以暖白、石墨灰为基础，主点缀使用更淡的雾蓝灰，可少量使用浅金、浅红土等辅助色，不以绿色或高饱和颜色作为主色。

普通球员模式包含五个底部入口：首页、训练、创建、消息、我的。创建入口以中间突出加号呈现，点击后先显示两个一级选择：“发布动态”和“创建网球日记”。发布动态进入真实 Post 发布流程，属于社区分享，可以单独发布，也可以后续从某条 Tennis Activity 选择片段、数据卡片或总结发布；单独发布动态不会自动创建 Tennis Activity。创建网球日记进入二级选择，包含记录练习、记录比赛和记录课程三项，底层都创建 `tennis_activities`。三种日记都支持不选视频直接保存，也支持从相册选择视频后随日记一起上传；有视频时使用上传草稿流程，全部文件完成后再提交 Activity 进入分析队列。记录练习和记录比赛可创建个人 Activity，当前 App 只暴露“仅自己”和“公开”两个可见范围；记录课程必须绑定当前用户参与的课程，创建 `activity_type = lesson_practice` 的 Activity，可见范围包含“仅自己”“教练可见”和“全课可见”。

首页用于网球社交 Post 内容流展示，顶部直接呈现推荐、关注、附近三个频道，不显示无信息价值的大标题或通知入口。首页不再使用本地模拟动态或模拟附近球友，统一调用 `GET /api/v1/posts/feed`。推荐频道允许未登录用户浏览公开且审核通过的 Post；已登录用户会额外过滤拉黑关系、主动隐藏，并把已浏览内容排到未浏览内容之后。关注频道只展示当前用户已关注作者的可见 Post，未登录时展示登录入口。附近频道只查询带公开粗粒度位置的 Post，App 端由用户选择城市或地区，不读取或展示精确坐标。Post 卡片点击媒体、标题或正文进入 Post 详情页，点击发布者头像进入发布者主页；点赞、评论和收藏按钮必须有明确反馈，评论按钮进入详情页评论区。

首页内容流使用稳定游标分页，不使用传统页码分页。下拉刷新只重新请求新的内容，不清空服务端浏览记录；加载到底部时展示明确的无更多内容状态。前端不会在接口返回时立即标记已看，而是在 Post 进入可见区域后通过 `POST /api/v1/posts/views/bulk` 批量上报浏览记录，并按卡片处于主要可视区域的时间累计 `dwell_time_ms`。浏览上报属于非阻塞的轻量行为，临时失败时客户端可静默重试，不应触发启动诊断弹窗或影响用户进入首页。当前 App 首页不提供单条隐藏动态入口；既有隐藏数据只作为服务端过滤兼容，不在移动端第一版暴露。推荐排序采用“未浏览优先、已浏览后置”的发布时间倒序策略，后续可替换策略但保持接口稳定。

首页动态卡片中的视频使用可见性驱动播放：当卡片达到主要可见区域并成为当前中心卡片时自动静音播放，其他卡片暂停；滑动切换时只保留一个活跃播放器，视频列表使用有限渲染窗口和封面占位以控制性能。卡片仍保持现有卡片式信息和互动布局，点击媒体、标题或正文进入沉浸式 Post 详情流。

训练页用于普通球员查看训练概览和进入创建流程。当前代码中，本周概览、图表和最近活动列表仍使用本地演示数据；记录区提供练习、比赛和课程三个入口，均进入真实 `create-activity` 流程并按 `kind = practice | match | lesson` 展示差异化表单。真实个人 Activity 列表当前以“我的”页面中的比赛、训练和课程 Tab 为准，后续训练页接入真实数据时应复用现有 `GET /api/v1/me/profile-content` 或新增活动列表接口。

消息页包含通知、聊天和请求三个视图，已登录用户统一从后端读取真实通知、私信会话、待处理消息请求和未读数；未登录用户展示登录入口。消息页右上角提供“添加球友”入口，进入球友搜索页后可按昵称或球友 ID 搜索用户，搜索结果进入用户主页完成关注或回关。聊天项进入真实单聊页，支持文本消息拉取、发送、发送中、发送失败重试、加载更早消息和进入会话后标记已读。会话中的 Post 站内分享以卡片展示当前可访问的标题、作者、摘要和可选缩略图；点击进入真实 Post 详情页重新校验权限。Post 被删除、隐藏或对当前会话成员不可见时，卡片仅显示内容不可用，不保留旧内容。聊天页支持选择一张本地图片或视频，使用消息专用上传接口完成校验和缩略图生成后发送对应媒体消息；视频显示首帧和时长，不提供完整播放器。视频的上传中、可重试失败、永久失败、取消和不可用状态在输入区安全展示；重试会重用独立的上传和消息幂等键，重启后恢复本地发送记录，避免重复创建消息。消息媒体与 Post 和网球日记上传完全隔离，原文件与缩略图使用独立生命周期，缩略图生成失败不删除原文件；过期、失败、取消媒体及孤儿文件由消息媒体清理任务治理，清理默认 dry-run，只有显式执行才删除。相同分享请求在网络重试时只保留一条分享和一条消息；幂等键参数冲突会稳定返回冲突错误且不重复计数。短期内，聊天详情页在前台聚焦时使用轻量轮询刷新新消息；后续接入 WebSocket 或移动推送时，应保留 REST 拉取作为断线补偿。消息页不放设置入口，设置归属于我的页面。

开发期 App 内置统一诊断弹窗，用于展示前端运行时错误、未处理 Promise、后端接口失败和对应的 request id；该能力仅用于调试和分析，不作为正式用户功能描述。

我的页面默认进入球员模式，采用内容型个人主页结构，展示头像、昵称和基础统计。普通用户的主视图不常驻展示教练身份状态或申请入口；已通过教练身份的用户可在右上角看到小型教练入口按钮。球员模式下，内容 Tab 按“动态、比赛、训练、课程、收藏、赞过、数据”横向排列，点击后在下方直接切换对应内容窗口；我的动态、收藏和赞过使用铺满式两列内容网格，比赛、训练和课程使用列表。“数据”Tab 当前只展示本地静态阶段状态，不代表已接入真实 AI 分析指标。

我的页面右上角提供三横线功能菜单，从右侧滑出功能入口列表，包含账号资料、教练身份和设置。退出登录不直接放在抽屉中，而是位于设置页底部并要求用户确认。教练申请入口保留在功能菜单中，普通用户不在主页面看到教练身份说明；普通用户、已撤销等非教练状态在菜单中只展示为申请入口，避免把少数用户场景做成高优先级主视图内容。

教练模式是独立的教学工作台，不是普通个人主页。当前 App 先根据 `GET /api/v1/users/me/coach-identity` 返回的身份和能力控制是否显示教练入口、课程管理、学员管理、视频点评、服务发布和学员咨询等能力。认证教练工作台、非职业教练可用服务、学员列表、最近课程、待点评视频、教学记录和学员档案页当前仍使用本地演示数据确认信息架构；后续接入真实课程、学员和点评接口时，应保持教练工作台与普通个人主页分离。

## 15. 教练身份申请与审核

系统中所有用户默认都是普通网球用户。教练身份不是独立账号，而是普通用户账号上的扩展身份。

教练分为两类：认证教练和非职业教练。认证教练需要选择资质名称、上传正式教练资质证明图片并填写必要资料，通过管理员审核后前端显示“认证教练”，可使用完整教练功能，包括教练主页、课程管理、学员管理和视频点评。资质名称选项包括：中国网球协会教练员证书、ITF 相关认证、PTR / USPTA / RPT 等国际认证、社会体育指导员证书、体育专业学历或教师证明、俱乐部任职证明、其他。非职业教练需要提交打球、教学或技术展示视频和基础资料，通过审核后前端显示“非职业教练”，可使用部分教练功能，包括发布基础教学服务、做视频点评和接收学员咨询；前端不展示认证教练资质标识。

用户端流程为：进入“教练身份”或“申请成为教练”，选择认证教练或非职业教练，按类型填写资料并提交材料。提交后进入审核中状态；审核通过后获得对应教练身份；审核拒绝后保留普通用户身份，并展示拒绝原因，用户可修改资料后重新申请。

当前移动端认证教练材料通过相册选择图片后写入 `certification_file_path` 字段提交，字段可以是后端受控路径、外部 URL 或开发期 image data URI；非职业教练的 `verification_video_path` 当前通过路径或 URL 填写。后续接入独立材料文件上传时，应把图片和展示视频保存到受控存储路径，再将路径写入申请字段，不改变 `coach_applications` 与 `coach_profiles` 的身份模型。

后台流程为：管理员查看教练申请列表和详情，对待审核申请执行通过或拒绝。拒绝时必须填写拒绝原因。管理员可以暂停、恢复或撤销已通过的教练身份。暂停和撤销后，用户端教练功能权限失效。

后端使用 `coach_applications` 保存每次申请和审核历史，使用 `coach_profiles` 保存已通过的教练扩展身份。`users.is_coach`、`users.coach_status`、`users.coach_verified_at` 仅作为兼容字段和列表筛选字段；前端身份展示和后端权限判断以 `coach_profiles` 与最新申请状态为准。

## 16. Admin Web 后台管理

系统新增独立的 `admin/` Web 前端项目，用于后台运营和管理员管理平台数据。Admin Web 不包含独立后端，不直接访问数据库，只调用现有 backend 提供的管理员接口。

后台管理接口统一位于 `/api/v1/admin/*`，与用户端 `/api/v1/auth/*`、`/api/v1/users/*` 等业务入口分开。管理员可以通过 `/api/v1/admin/auth/login` 使用后台用户名密码登录并换取现有 Bearer token；管理员接口使用该 token 识别当前用户，再通过 `admin_users` 授权表校验后台权限。后台用户名密码凭据保存在 `admin_credentials` 表中，密码只保存 PBKDF2 hash，不保存明文。普通用户即使已登录，也不能访问后台接口。

当前第一版 Admin Web 覆盖用户、教练申请、`tennis_activity`、视频和 Post 等核心管理对象。用户、活动、视频和 Post 模块提供列表、搜索、状态筛选、分页、详情查看、新增、编辑和软删除等基础管理操作；教练申请模块提供列表、搜索、状态筛选、详情查看、通过、拒绝、暂停、恢复和撤销操作。Admin Web 页面右上角可配置 API Base URL 和管理员 Bearer token，也可通过后台用户名密码调用 `/api/v1/admin/auth/login` 获取 token。接口暂未接通或本地开发需要时，前端可以手动启用演示数据用于确认信息架构和操作流程；接入真实管理员接口时，应通过管理员 Bearer token 调用 backend。

Admin Web 的快速操作不引入独立工作流服务。用户启用、禁用和软删除通过用户管理 PATCH/DELETE 完成；Activity 公开/私密和“重跑汇总”通过更新 `default_visibility` 或 `analysis_summary_status = pending` 表达；视频“重新排队”和“取消分析”通过更新 `analysis_status` 表达；Post 发布、隐藏、恢复草稿和软删除通过 Post 状态更新或软删除表达；教练审核、暂停、恢复和撤销使用专门的管理员教练接口。

Admin Web 不直接访问数据库，不包含独立后端。后台权限继续由 `admin_users` 和 `admin_credentials` 表表达；教练审核由 backend 管理员接口完成。后续新增管理员功能时，应继续保持后台管理前端与 backend API、数据库和移动端用户体验解耦。

## 17. App 视频上传

视频上传是 Tennis Activity 的素材能力，不作为创建加号菜单的独立一级入口展示；创建网球日记的三种表单都直接提供相册视频选择。视频上传流程仍保留为 Activity 附件和后续分析能力：一次上传会先创建一条 `tennis_activities` 草稿，再在该 activity 下创建一组 `videos` 记录，随后逐个上传原始视频文件；视频不直接挂在 `lessons` 表上。第一版上传入口从手机相册选择视频；一次 Activity 上传当前最多选择 20 个视频，App 与后端 `UploadIntentCreate.videos` 都按该上限校验。拍摄入口待相机录制流程接入后再恢复。

上传视频本质上是在创建带视频的 Tennis Activity。归档方式分为个人活动、课程练习和教学示范。个人活动不关联课程，可选择 `casual_hit`、`match`、`serve_training`、`forehand_training`、`backhand_training`、`multi_ball_drill`、`stroke_recording`、`post_match_review` 或 `other`，默认 `default_visibility = private`。课程练习必须选择当前用户参与的课程，使用 `activity_type = lesson_practice`，默认可见性为 `lesson_coach`。教学示范仅通过教练身份审核的用户可用，使用 `activity_type = coach_demo`；如果关联课程，默认可见性为 `lesson_participants`，否则默认为 `private`。

创建无视频 Activity 和上传视频创建 Activity 时，移动端不再要求用户手填地点。App 打开后启动前台位置缓存，优先从手机系统读取经纬度、定位精度和定位时间，并在前台每 3 分钟刷新一次；记录练习、记录比赛、记录课程、附近动态等非视频元数据场景需要位置时，优先直接使用上一次缓存的经纬度，避免每个功能现场等待定位。上传视频或发布视频动态时，如果所选视频的相册资产包含拍摄经纬度，App 优先使用该拍摄位置并保存为 `location_source = video_metadata`；如果视频没有位置元数据，再使用前台位置缓存。拿到经纬度后调用 `POST /api/v1/locations/resolve` 由后端解析省、市、区。用户拒绝定位权限、系统定位服务未开启，或手机无法在合理时间内返回经纬度时，Activity 仍可保存，但 `location_source = unavailable`；不再使用网络/IP 粗略定位兜底。手机或视频已返回经纬度且后端边界数据可用时，后端必须返回精确命中或最近行政区近似结果；只有解析依赖、边界数据不可用或客户端请求超时时，App 才保留经纬度并允许省、市、区暂时为空。Activity 精确经纬度只作为活动私有数据返回给活动所有者和后台管理，不向其他用户公开；非所有者查看可见 Activity 时只返回城市、区等粗粒度位置。`location_name` 保留为旧数据兼容和粗粒度展示字段，后续球场识别通过已保存的精确位置匹配候选球场。

行政区解析第一版不引入 PostGIS。后端通过 `TENNIS_AREA_CITY_BOUNDARY_PATH` 指向 AreaCity 三级行政区边界数据，默认路径为 `backend/data/area_city_ok_geo.csv`，支持 AreaCity 原始 `ok_geo.csv` 的 `polygon` 边界字段和 GeoJSON/JSON 边界文件；解析时使用 Python Shapely 和 STRtree 空间索引做点面匹配。App 采集坐标统一按 `wgs84` 提交；边界数据坐标系通过 `TENNIS_AREA_CITY_COORDINATE_SYSTEM` 配置，默认 `gcj02`，查询前由后端完成 WGS84/GCJ-02 转换。后端 API 启动时预热边界索引，避免手机首次解析承担大文件加载成本；App 仍设置有限超时，防止异常环境下长时间转圈。

后端提供用户侧上传 API：`GET /api/v1/lessons/mine` 返回当前用户可绑定的课程；`POST /api/v1/tennis-activities` 创建无视频 Activity 记录，用于记录练习、比赛或绑定课程后的课程练习；`POST /api/v1/tennis-activities/upload-intents` 创建 activity 与待上传视频记录；`POST /api/v1/videos/{video_id}/file` 上传单个视频文件；`POST /api/v1/tennis-activities/{id}/complete-upload` 在全部视频上传完成后提交 activity 并把视频分析状态置为待处理；`POST /api/v1/tennis-activities/{id}/cancel-upload` 可取消尚未完成的上传草稿。移动端上传大视频时必须区分文件传输、服务端保存/预览图生成、提交 Activity 和进入分析队列等阶段，避免进度到 100% 后只显示无说明的等待动画。

视频文件上传状态使用 `videos.upload_status` 表达，取值为 `pending`、`uploading`、`uploaded`、`failed`、`canceled`。该状态只描述文件上传生命周期，不替代 `videos.analysis_status`。第一版支持常见视频文件后缀 `mp4`、`mov`、`m4v`、`webm`、`mkv`、`avi`，并兼容 iOS 录制 MOV 常见的 QuickTime MIME 类型。创建上传意图时客户端传入的 `file_size_bytes` 仅表示选中素材的本地报告大小，可用于展示和提前提示；上传完成后以后端实际接收到的字节数写回 `videos.file_size_bytes`，不应仅因二者不完全一致判定上传失败。上传完成后，文件保存到后端配置的本地视频存储目录，并通过 `/storage/videos/...` 暴露给本地开发预览；后端同时为所有已上传视频生成并保存 `videos.thumbnail_path`，Tennis Activity 视频、手机直传 Post 视频和 Post 引用的 Activity clip 都使用同一缩略图字段。后续接入云存储或断点续传时，应保持 activity/video 业务模型不变，仅替换文件存储和上传传输层。

## 18. 我的内容页真实数据

移动端“我的”页面中，球员模式下的“动态”“比赛”“训练”“课程”四个内容页应显示当前登录用户自己的真实数据，不再只依赖本地演示数据。页面进入或重新聚焦时通过 `GET /api/v1/me/profile-content` 拉取聚合内容，并同步刷新顶部统计数字。“收藏”和“赞过”不塞进该聚合接口，而是在 Tab 打开时按需调用独立的游标分页接口。

“动态”显示当前用户发布或保存为草稿的 `social_posts`，按发布时间或创建时间倒序排列；每个动态卡片优先展示图片或首个视频缩略图，点击后进入 Post 详情页。若动态关联了 `source_tennis_activity_id`，Post 详情页再提供来源 activity 入口。发布动态入口位于中间创建菜单，不在“我的”页面内直接编辑发布。

“比赛”显示 `tennis_activities.owner_user_id = 当前用户` 且 `activity_type = match` 的 activity，包括记录比赛创建的无视频记录和比赛录像上传创建的带视频记录。“训练”显示当前用户除比赛外的 activity，包括记录练习创建的无视频记录、日常视频上传、课程练习视频和教练教学示范视频；刚完成上传并进入 `analysis_status = queued` 的 activity 必须立即出现在训练列表中。每条 activity 展示标题、时间、地点、视频数量、上传状态和分析状态；无视频记录展示为“无视频”和“暂无分析”，不显示成上传失败。

“课程”显示当前用户作为教练或学员参与的 `lessons`。课程条目展示用户在该课程中的角色、课程状态、时间、关联 activity 数和视频数。课程仍是教学组织对象，视频通过 `tennis_activities.lesson_id` 间接归入课程。

四个内容页都需要处理加载、失败和空状态：加载时显示进度反馈；失败时显示错误和重试入口；无内容时显示对应空状态说明。未登录用户仍显示登录入口，不请求个人内容接口。

“收藏”调用 `GET /api/v1/me/favorite-posts`，显示当前用户主动收藏的动态；“赞过”调用 `GET /api/v1/me/liked-posts`，显示当前用户点过赞的动态。两者按对应互动时间倒序分页，只返回当前用户仍有权限查看的已发布、审核通过动态，并排除已隐藏、被拉黑或作者已失效的内容。卡片沿用首页 Post 卡片的媒体、作者、统计和 viewer state 数据。用户在卡片上取消收藏或取消点赞后，当前列表立即移除该动态。

球员模式“数据”Tab 当前不请求后端分析结果，只显示本地阶段状态占位。真实技术指标、训练趋势和 AI 建议接入后，应优先来自 CV/analysis 输出或后端分析聚合接口，不应继续在个人主页中写死展示值。

## 19. Activity 详情页与视频播放

移动端从上传完成提示、记录练习/比赛/课程完成提示、Post 来源 Activity 入口、“我的”页面中的比赛/训练列表，以及后续训练页真实列表进入 `/activity/[id]` 时，应展示真实 `tennis_activities` 详情，不再使用本地假 activity。详情页第一屏以视频播放和活动识别为核心：顶部显示返回、标题和 activity 类型；主区域展示当前选中的已上传视频；下方展示时间、场地、视频数、上传状态、分析状态和当前用户是否可管理。

详情页通过 `GET /api/v1/tennis-activities/{id}` 获取数据。后端返回 activity、当前用户可见的视频列表、可选 lesson 上下文、权限和聚合状态。App 端只播放后端返回且 `upload_status = uploaded` 的视频；待上传、上传失败、取消或无可播放文件时展示明确空状态，不进入播放器。

一次 activity 可包含多个视频。详情页应提供视频列表，展示缩略图、文件名、大小、时长、上传状态、分析状态和上传时间；点击某个已上传视频后，主播放器切换到该视频。App 使用 `expo-video` 承载播放器，详情页只挂载一个主播放器，避免多个播放器同时渲染造成性能和平台兼容问题。

如果 activity 关联了 `lesson_id`，详情页展示课程上下文卡片，包括课程标题、当前用户在课程中的角色、课程状态、上课时间、场地、训练内容、课后作业和下节重点。课程只是组织教学上下文，视频仍归属于 activity 和视频记录本身。

详情页中的“数据”和“建议”必须反映真实分析状态。分析未完成时显示等待分析、分析中或暂无分析结果，不使用假图表或假建议冒充真实结果。后续接入 AI 分析输出后，再在该页面填充技术指标、动作建议、教练点评和复盘内容。

## 20. Post 发布

移动端“创建”菜单中的“发布动态”进入真实 Post 发布流程。第一版支持从手机相册选择一段短视频发布动态，单条 Post 最多 1 个视频，视频时长后端硬限制为 10 分钟。客户端在选择视频时先根据本地媒体信息拦截超长视频；后端创建上传意图和发布时再次校验 `video_duration_ms`，避免绕过客户端限制。当前 App 发布页只暴露“公开”和“仅自己”两个可见范围；后端用户侧 Post API 已支持 `friends` 和 `followers`，`specified_users` 仍保留为后续指定可见列表能力。

手机直传动态只创建 `social_posts`、`post_media` 和一条独立 `videos` 记录，不自动创建 `tennis_activities`。这类视频的 `videos.tennis_activity_id = NULL`，表示它是动态素材，不属于一次训练或比赛记录，也不会出现在训练列表中。发布动态不会改变原始视频、原始 activity 或课程视频的隐私设置。

发布动态不让用户手填精确地点。App 优先读取所选视频的拍摄经纬度；视频没有位置元数据时，使用前台手机定位缓存，并在拿到经纬度后调用后端行政区解析接口。Post API 只接收并保存 `location_scope`、`location_region` 和 `location_city`，不保存精确经纬度；没有视频或手机经纬度、未授权、边界数据不可用或解析请求超时时，该 Post 不进入附近内容流。附近流同样通过前台手机定位缓存得到城市或地区作为查询条件，不使用网络/IP 粗定位兜底，只返回粗粒度位置语义，不向其他用户暴露精确位置。

后端提供用户侧 Post API：`POST /api/v1/posts/upload-intents` 创建 draft Post、动态媒体、待上传视频和统计记录；`POST /api/v1/videos/{video_id}/file` 复用现有视频文件上传接口并生成视频缩略图；`POST /api/v1/posts/{id}/publish` 在视频上传完成后发布动态；`GET /api/v1/posts/{id}` 返回当前访问者可读的统一 Post 详情，作者本人可查看自己未删除的草稿、私密、审核中或已发布动态，非作者只能查看已发布、审核通过且权限允许的动态，并在登录时返回 `viewer_state` 表示当前用户是否已点赞或收藏；`GET /api/v1/posts/public/{id}` 保留为已发布可读详情的兼容入口；`PATCH /api/v1/posts/{id}` 更新标题、正文、可见性和粗粒度位置；`DELETE /api/v1/posts/{id}` 软删除动态，draft 删除时会取消对应的独立动态视频；`GET /api/v1/posts/feed` 返回推荐、关注或附近内容流；`POST /api/v1/posts/views/bulk` 批量上报实际浏览。

Post 详情页采用沉浸式全屏视频播放结构：视频或缩略图铺满屏幕，返回、点赞、评论、收藏、发布者、发布时间、视频时长、标题和正文叠加在视频上。从首页内容流、收藏或赞过列表等已经持有完整 Post 详情的入口进入时，App 可以先复用入口数据立即渲染视频播放，再后台刷新 `GET /api/v1/posts/{id}` 获取最新互动状态和权限结果；没有入口详情缓存时再展示加载态。详情页从首页进入时携带当前内容流中的 Post 顺序，使用全屏纵向分页流支持上下滑切换视频；切换到下一条时刷新当前详情、互动状态和评论上下文，并只挂载当前页的真实播放器，邻近页面优先显示封面以控制性能和平台兼容性。详情页视频支持加载中、暂停/继续、无可播放视频等状态，并在暂停、离开页面或重新上报时累计观看时长到 `dwell_time_ms`，观看时长只作为后台行为数据，不在用户界面展示。点赞和收藏在登录后直接切换状态；评论按钮打开底部评论层，支持查看公开可见评论并在登录后提交评论。若 Post 关联了来源 activity，详情页提供进入来源 activity 的悬浮入口。

为后续剪辑功能预留的数据模型已经生效：从 Tennis Activity 选择片段发布时，Post 使用 `social_posts.source_tennis_activity_id` 记录来源活动，`post_media.media_type = video_clip`，并保存 `video_id`、`clip_start_ms` 和 `clip_end_ms`。剪辑功能本期不在 App UI 中实现，后续剪辑器只需要产出来源视频和片段时间范围。

## 21. 社交关系与消息中心

第一版后端已经接入真实社交关系、Post 互动、消息请求、隐私、举报和消息中心数据模型。移动端消息页已经从后端接口读取通知、会话、消息请求和未读计数，不再依赖本地模拟内容。当前 App 已暴露关注/取消关注、发布者主页、私信、消息请求、点赞、评论、回复、删除评论、收藏和 Post 站内分享；拉黑、隐私设置、举报、外部分享、群聊创建和复杂群管理主要停留在后端接口、数据库模型或 shared schema，移动端第一版尚未提供完整入口。

用户关系使用关注事实表达：`user_follows` 保存 A 关注 B；当 A 关注 B 且 B 关注 A 时，接口返回 `is_friend = true`，视为好友/球友关系。系统不设计独立好友申请流程。点击动态作者头像或球友搜索结果进入发布者主页，主页展示关注、回关、已关注、已互关等关系状态，并提供“发消息”入口。关注用户会为被关注者生成一条互动通知。取消关注只取消单向关注关系，不删除历史记录。

第一阶段添加球友提供搜索式入口，不接入扫码、通讯录或手机号搜索。`GET /api/v1/users/search` 仅对已登录用户开放，支持昵称包含匹配和球友 ID 前缀匹配，结果只返回头像、昵称、教练状态和当前关系状态，不返回手机号或邮箱；被拉黑关系、禁用/删除用户和对陌生人隐藏资料的用户不会出现在陌生人的搜索结果中。

Post 互动使用事实表表达：点赞写入 `post_reactions`，收藏写入 `post_favorites`，评论和回复统一写入 `post_comments`，分享写入 `post_shares`。`social_post_stats` 只作为点赞数、评论数、收藏数、分享数和浏览数的展示/排序缓存，不替代事实表。重复点赞和收藏通过数据库唯一约束避免；取消点赞和取消收藏只更新状态，不删除历史记录。点赞、评论和回复会生成互动通知。

聊天使用 `chat_conversations`、`chat_conversation_members`、`chat_messages` 和 `chat_message_attachments` 表达。私信会话通过双方用户 ID 生成唯一 `direct_pair_key`，保证两个用户之间只有一个有效私信会话。后端接口支持创建基础群聊，但移动端第一版暂未暴露群聊创建入口，也不包含复杂群管理。消息发送后立即落库，并递增其他成员的 `unread_count`；对方不在线时消息仍然保存在数据库中，用户下次进入消息页通过会话列表和未读数拉取。

消息内容不只支持文字。`chat_messages.message_type` 预留文字、图片、视频、语音、文件、Post 分享、视频分享、Activity 分享、课程分享和 AI 分析卡片等类型。业务对象通过 `target_object_type`、`target_object_id`、`context_object_type`、`context_object_id` 通用引用，不把 `videos`、`social_posts`、`tennis_activities`、`lessons` 等业务字段硬耦合进消息表。

陌生人消息请求使用 `chat_message_requests` 表达。默认私信策略为 `friends`，即互相关注后可以直接创建私信会话；不满足直聊策略但对方允许消息请求时，用户可在发布者主页的“发消息”流程中提交消息请求。接收方在消息页“请求”视图接受请求后创建或复用双方私信会话，拒绝或拉黑后该 pending 请求结束。

通知使用 `notification_events` 和 `user_notifications` 两层模型。事件表记录一次业务事件，用户通知表记录某个接收者的通知状态、已读状态和展示状态。第一版支持关注通知和基础通知列表，后续可复用同一模型接入点赞、评论、@、AI 分析完成、课程变更、教练审核等通知。

拉黑使用 `user_blocks` 表达。拉黑后禁止关注、私信和群聊邀请，并取消双方已有关注关系；取消拉黑不会自动恢复关注关系。基础隐私设置使用 `user_privacy_settings` 表达，第一版支持私信策略、是否接受消息请求、默认 Post 可见性和陌生人资料可见开关。举报使用 `content_reports` 表达，同一用户对同一对象只保留一条待处理举报。

用户侧接口包括：Post 点赞/取消点赞、收藏/取消收藏、评论/回复/删除评论、分享、关注/取消关注、粉丝/关注/好友列表、关系判断、拉黑/取消拉黑/拉黑列表、隐私设置、举报、创建私信会话、创建基础群聊、消息请求创建/列表/接受/拒绝、发送消息、拉取会话列表、拉取消息列表、标记会话已读、未读计数、通知列表、通知已读和全部已读。实时 WebSocket、移动推送、消息搜索、复杂群权限和端到端加密不属于第一阶段。

## 22. 数据库运行时

后端运行时统一使用 PostgreSQL 作为唯一业务数据库；SQLite 仅保留为一次性旧数据读取和迁移输入，不参与 API、任务或 CV 运行时。数据库迁移不改变 Post 或网球日记上传接口，也不新增视频、音频或文件消息。CV 历史表继续使用原字段，并置于独立的 `cv_analysis` schema。

消息历史、搜索和 reconcile 保持 `message_seq` 游标语义；Post
业务对象卡片在单页内批量 hydration，不复制完整业务对象。迁移审计和
性能结果分别记录，消息媒体文件不随数据库迁移，需独立
执行生命周期治理。

## 23. 本地发送与离线恢复

消息草稿和待发送消息在移动端本地保存。断网或应用重启后，`queued`/`sending`
记录可以恢复；发送前生成 `client_message_id`，服务端 `message_id` 和
`event_id` 是权威结果，客户端按 client key 合并，避免超时重试重复渲染。

服务端提供 durable Outbox 事件和只读事件游标，并在消息、会话预览及未读状态
同一事务中提交。该基础不接入 Push、WebSocket/SSE；消息反应、转发、
输入状态、在线状态、端到端加密和复杂群治理仍未实现。

消息模块补充专用视频上传和视频消息：支持本地测试存储、视频真实内容
校验、首帧缩略图、鉴权读取、取消/过期/清理和消息事务绑定；不包含转码、
直播、Push、WebSocket/SSE、反应、转发或复杂群治理。
